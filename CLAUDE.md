# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projeto

O CareTrack é uma aplicação web de acompanhamento de pacientes (informações clínicas, registros de evolução, acompanhamento multidisciplinar). Este repositório contém **apenas o frontend**: Next.js 16 (App Router), React 19, TypeScript e Tailwind CSS v4. Todos os dados vêm de um backend REST separado. O navegador fala só com a origem do front: o `next.config.ts` repassa (rewrite) `/api/v1/*` para a API em `API_URL` (variável só do servidor, definida em `.env.local`; o build falha sem ela). Assim o cookie de sessão fica no domínio do front, qualquer que seja o domínio da API. `STORAGE_ORIGIN` (opcional, também só do servidor) é a origem do storage dos anexos, liberada na CSP para exibir fotos e vídeos pela URL assinada; sem ela, a CSP bloqueia os anexos no visualizador e o Next avisa no terminal. Em desenvolvimento, use o `S3_PUBLIC_ENDPOINT` da API ou, se ele estiver vazio, o `S3_ENDPOINT` (ex.: `STORAGE_ORIGIN=http://localhost:8333`). Detalhes e requisitos de deploy em `ROADMAP.md` (Acordos com a API).

Textos da interface, mensagens de toast e erros de validação são em **português do Brasil**; mantenha novos textos voltados ao usuário em português.

## Comandos

```bash
npm run dev     # servidor de desenvolvimento em http://localhost:3000
npm run build   # build de produção (também faz a checagem de tipos)
npm run lint    # ESLint (eslint-config-next)
npm run typecheck   # next typegen + tsc --noEmit (o next-env.d.ts não é versionado)
npm run check   # lint + typecheck + testes + build, o mesmo do CI
npm test        # testes unitários e de componentes (Vitest)
npx vitest run lib/masks.test.ts   # um arquivo só
npm run test:e2e   # fluxos no navegador (Playwright), sobre o build de produção na porta 3100
```

### Testes

- **Vitest + Testing Library** (`vitest.config.mts`, ambiente jsdom, `vitest.setup.ts`): arquivos `*.test.ts(x)` ao lado do código testado. Componentes e hooks que usam TanStack Query são renderizados com `renderWithQueryClient` / `renderHookWithQueryClient` (`test/render.tsx`, sem retry). Mocke os services (`vi.mock("@/services/...")`), o `next/navigation` e o `react-toastify`, nunca o axios dentro de um hook; o interceptor do `lib/api.ts` tem teste próprio, com um `adapter` falso. O jsdom não implementa o `<dialog>` (o setup tem um polyfill mínimo de `showModal`/`close`) nem layout: foco ao abrir diálogo, CSP e navegação ficam para o Playwright.
- **Playwright** (`playwright.config.ts`, pasta `e2e/`): roda sobre `next build` + `next start` na porta 3100, com `API_URL` apontando para um endereço morto. A API é simulada no navegador pelo fixture `api` (`e2e/fixtures.ts`, `page.route` em `/api/v1/**`), que guarda o estado do login e grava o cookie `token` para o `proxy.ts`; `test.use({ apiOptions: { signedIn: true } })` começa logado. Rota nova da API usada num fluxo entra no `FakeApi.handle`. O storage dos anexos é simulado em `STORAGE_ORIGIN` (`https://storage.e2e.test`, definido no `playwright.config.ts`), que devolve um PNG; enviar arquivo no teste é com `setInputFiles` no `input[type="file"]`. O fixture `cspViolations` coleta as violações de CSP do console: página nova deve ter um teste que confere que a lista fica vazia. A acessibilidade é verificada com o axe (`@axe-core/playwright`, WCAG 2.2 A/AA) em `e2e/accessibility.spec.ts`: página ou diálogo novo entra lá, inclusive no estado com erros de validação. Para timers da sessão, use `page.clock`. Os dados dos testes são fictícios.
- **CI** (`.github/workflows/ci.yml`, no mesmo modelo do `care-track-api`): roda em PRs para `master`/`develop` e em push na `develop`. Jobs: `npm run check`; Playwright (instala o Chromium; em falha, os traces vão como artefato por 7 dias, só dados fictícios); e, só em PR, commitlint sobre os commits do PR, com rejeição de mensagens vazias. O `API_URL` do CI aponta para um endereço morto. O Node vem do `.nvmrc` (Node 24/npm 11: o Dependabot gera o lockfile com o npm 11). O Dependabot (`.github/dependabot.yml`) abre PRs semanais para a `develop` (npm e actions), sem major de `@types/node` e `typescript`. Pacotes que precisam subir juntos ficam num grupo (`react` com `react-dom` e os tipos; `next` com `eslint-config-next`): dependência nova nessa situação entra num grupo, senão o PR isolado quebra o `npm ci`. Ainda não há semantic-release nem imagem Docker: dependem da topologia de deploy (ver `ROADMAP.md`).

## Git

O desenvolvimento acontece na `develop`; os PRs têm como alvo a `master`. Commits seguem Conventional Commits, validados pelo commitlint (regras em `docs/commits.md`). Git hooks (husky): `pre-commit` roda o lint, `commit-msg` o commitlint e `pre-push` os testes e o build.

## Arquitetura

Os dados fluem em camadas; siga a mesma divisão ao adicionar funcionalidades:

1. **`lib/api.ts`** — instância única e compartilhada do axios, com `baseURL` relativa `/api/v1` (só funciona no navegador; a autenticação é baseada no cookie httpOnly `token`, nenhum token é manipulado no cliente). Um interceptor de resposta:
   - em caso de **401**, redireciona para `/login?expired=true` (exceto se já estiver em `/login` ou se a requisição usar `{ skipAuthRedirect: true }`, como `getCurrentUser`);
   - converte todo erro do axios em `ApiError` (`shared/ApiError.ts`) com `message` (texto em português da API, ou um genérico como fallback), `statusCode`, `code` (identificador estável do erro na API, ex.: `PATIENT_ARCHIVED`), `requestId` (header `x-request-id`) e `errors` (os erros por campo do 422, `{ location, path, message }`). **Decida o tratamento pelo `code`** (`hasErrorCode(err, "...")`), nunca comparando a `message`; os códigos estão no schema `Error` do OpenAPI da API.
2. **`services/*.service.ts`** — funções assíncronas simples que encapsulam as chamadas ao `api` e retornam `response.data`. Os tipos de resposta ficam em `model/`.
3. **`hooks/<domínio>/use*.ts`** — hooks de cliente consumidos pelos componentes. Leituras usam `useQuery` do TanStack Query com chaves de `lib/query-keys.ts` (centralize novas chaves lá). Escritas usam `useMutation` com `onError: notifyError` (`lib/notify-error.tsx`, toast com a mensagem do `ApiError` ou uma genérica; em erro 5xx, mostra também o `requestId`), navegam com `useRouter` e expõem `{ <ação>: mutation.mutate, isPending }` — use `mutate` (não `mutateAsync`) para não gerar promises rejeitadas sem tratamento.
4. **Componentes** — formulários usam `react-hook-form` + `zodResolver`, com o schema Zod (v4) definido no próprio arquivo do componente. Os erros por campo do 422 vão para os campos com `applyFieldErrors` (`lib/form-errors.ts`): o hook da mutação recebe `onValidationError` e só mostra o toast quando sobra erro sem campo correspondente (ver `useCreatePatient`). Campo opcional vazio é omitido do corpo enviado à API (ela recusa `""` e `null`).

### Rotas (`app/`)

- `app/layout.tsx` — layout raiz: fundo em gradiente global, fonte Inter e tudo envolvido em `Providers` (`app/providers.tsx`: `QueryClientProvider` + `ToastContainer`). O `QueryClient` não repete consultas que falham com 4xx; só erros de rede/5xx são tentados até 3 vezes.
- `app/page.tsx` — landing page pública; `app/login` e `app/signup` — páginas públicas de autenticação que usam `app/ui/components/external-layout.tsx`. Componentes específicos de uma página ficam numa pasta `components/` ao lado dela.
- `app/verify-email` e `app/reset-password` — destinos dos links que a API envia por e-mail (`EMAIL_HOST` e `PASSWORD_RESET_HOST` no `.env` da API apontam para elas). A página (server component) lê o `?token=` de `searchParams` e passa como prop; o client component tira o token da URL com `history.replaceState` e o envia à API. Os tokens são de uso único: chame a API uma vez só (ref de guarda contra o Strict Mode). A API responde 422 com `code: "INVALID_LINK_TOKEN"` para token inválido/expirado/usado (`isInvalidTokenError` em `shared/ApiError.ts`); a confirmação de e-mail trata também `EMAIL_ALREADY_VERIFIED`. `app/forgot-password` pede o link de redefinição.
- `app/(legal)/` — páginas públicas `termos` e `privacidade`, com layout próprio. Os dados do responsável, do encarregado, dos fornecedores e os prazos ainda são marcadores entre colchetes, todos em `lib/legal.ts`: preencha lá, nunca no texto das páginas. O cadastro exige o aceite (checkbox) e envia `acceptedTermsVersion: TERMS_VERSION`, que a API grava com a data e hora. **Ao mudar o texto dos documentos, troque `TERMS_VERSION` e `TERMS_UPDATED_AT` em `lib/legal.ts` e a `CURRENT_TERMS_VERSION` da API juntos**: a API recusa (422) uma versão diferente da atual. Os links para os documentos (`app/ui/legal-links.tsx`) ficam no rodapé da landing, das páginas de autenticação e da área logada.
- `app/(authenticated)/` — route group das páginas para usuários logados: `pacientes` (página inicial após o login; o detalhe `pacientes/[id]` mostra, nesta ordem, o cabeçalho com as ações e o botão "Autorização de imagem", os dados cadastrais recolhíveis, a seção de anexos, que abre o carrossel e só aparece com anexos, e o histórico; a autorização de uso de imagem fica em `pacientes/[id]/autorizacoes`) e `perfil`, sob o cabeçalho com a navegação (`components/app-header.tsx`; destino novo no menu entra em `navItems`). O `/dashboard` antigo redireciona para `/pacientes` (`next.config.ts`). Seu `layout.tsx` é um client component que só renderiza a página depois que `useCurrentUser` confirma o usuário: mostra carregamento, uma tela de erro com "Tentar novamente" (falha de rede/500) ou redireciona para `/login?expired=true` em 401. As páginas de login, cadastro e esqueci a senha são envolvidas por `app/ui/components/guest-only.tsx`, que manda quem já está logado para `/pacientes`. O `proxy.ts` roda em todas as páginas e faz duas coisas: gera a Content-Security-Policy com um nonce novo por requisição (ver abaixo) e redireciona para `/login`, antes de renderizar, quem acessa a área logada sem o cookie `token`. Ele só verifica a presença do cookie, e o layout continua tratando o 401 de um cookie inválido. **Rota nova da área logada entra em `PROTECTED_PREFIXES` no `proxy.ts`** (fora dela, só o layout protege). O proxy não manda quem tem cookie para fora do `/login`: um cookie inválido causaria um loop entre `/login` e a área logada, por isso o `GuestOnly` confirma a sessão na API. O backend continua sendo a barreira real.
- Cabeçalhos de segurança: a CSP vem do `proxy.ts`, com nonce por requisição e `'strict-dynamic'` para scripts (o Next aplica o nonce sozinho aos scripts dele), `'unsafe-inline'` só para estilos (o `react-toastify` e o `next/image` usam estilo inline) e `connect-src 'self'` (o navegador só fala com o próprio front). Por isso o `app/layout.tsx` chama `await connection()` e todas as páginas são renderizadas por requisição: página estática não recebe nonce e teria os scripts bloqueados. Não adicione `<script>` inline nem scripts de outros domínios; um domínio externo necessário entra na diretiva certa do `contentSecurityPolicy`. O storage dos anexos (`STORAGE_ORIGIN`) já está em `img-src`, `media-src` e `frame-src`, e `frame-src` aceita `blob:` para a pré-visualização local de PDFs. O `X-Powered-By` está desligado (`poweredByHeader: false`). Os demais cabeçalhos (`X-Frame-Options`, `nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` sem câmera/microfone/localização, `Cross-Origin-Opener-Policy`, HSTS em produção) ficam no `next.config.ts`.
- Sessão e logout por inatividade: a sessão da API é deslizante (expira após 30 min sem requisições ou 12 h após o login). O interceptor do `lib/api.ts` guarda a expiração de cada resposta (`X-Session-Expires-At`, corrigida pelo header `Date` contra a diferença de relógio) no store em memória de `lib/session.ts`, que sincroniza as abas por `BroadcastChannel` (só horários, nunca dados pessoais). O `SessionTimeout` (`app/(authenticated)/components/session-timeout.tsx`) renova a sessão em silêncio quando há interação (teclado, clique, rolagem; no máximo um `GET /auth/me` a cada 5 min), avisa 2 min antes de expirar por inatividade e 5 min antes do limite de 12 h, e ao expirar limpa o cache e vai para `/login?expired=true`. O logout espera a renovação em andamento (`waitForPendingRenewal`), para que ela não recrie o cookie depois do signout, e encerra as outras abas. Não use `refetchInterval` nem polling na área logada: cada requisição renova a sessão, e o polling a manteria aberta sem ninguém no computador. Se a API mudar os 30 min, ajuste `SESSION_IDLE_TIMEOUT_MS`.
- Anexos (Fase 3): cada arquivo vai para `POST /patients/:id/attachments` (multipart, campo `file`) **antes** de salvar o registro, e o `POST` do registro recebe os `attachmentIds`; o registro pode ter só arquivos. A fila de envio é o `useAttachmentUploads` (`hooks/attachments/`): um arquivo por vez, com progresso, cancelar (o `AbortController` chega ao axios, e o interceptor do `lib/api.ts` repassa o cancelamento sem convertê-lo em `ApiError`), enviar de novo e remover. A validação no cliente (`lib/attachments.ts`) repete a da API: formatos de `ATTACHMENT_CONTENT_TYPES`, até 200 MiB, nome sem caractere de controle, até 20 por registro. Fotos e vídeos exigem autorização de imagem válida (`useImageConsent`, que usa o `needsRenewal` da API): sem ela, o arquivo nem é enviado, e o 409 `ATTACHMENT_CONSENT_REQUIRED` da API aparece no arquivo, com link para a página de autorizações (`consent-page-link.tsx`, que abre em nova aba para não descartar o registro em andamento; ao voltar, a consulta de autorizações recarrega com o foco da janela). A seção "Anexos" do detalhe (`patient-attachments.tsx`) usa a `GET /patients/:id/attachments` por cursor (`useAttachments`, chave `attachmentList`, separada das chaves de download para que invalidar a lista não peça URLs de novo) e, ao ser clicada, abre o `AttachmentViewer` como carrossel por todos os anexos, carregando a página seguinte perto do fim. Não há miniaturas (decisão de 11/11/2026, ver `ROADMAP.md`): nenhum arquivo do paciente aparece na tela sem uma ação do profissional. A visualização (`attachment-viewer.tsx`) busca a URL assinada só ao abrir o anexo (`useAttachmentDownload`, com `disposition=inline` e sem cache: cada pedido é auditado e a URL vale 5 min) e exibe imagem, vídeo ou PDF (`<iframe>`) pelo `FilePreview`; se a mídia falhar, pede outra URL uma vez, e o "Baixar arquivo" pede, no clique, uma URL com `attachment`. Antes de salvar, o "Visualizar" de cada arquivo (`upload-preview.tsx`) exibe o arquivo local por uma URL `blob:` do `useObjectUrl`, criada com o tipo detectado pela extensão (nunca o declarado pelo arquivo) e revogada ao desmontar; foto ou vídeo sem autorização de imagem não é exibido nem localmente. Os dois diálogos usam o `PreviewDialog` (título com "1 de N", ou "1 de N+" com mais páginas, Anterior/Próximo, e "Enviado em" quando recebe o `createdAt` do anexo salvo). A URL nunca é guardada fora da consulta aberta. Anexos não são editados nem apagados: saem junto com o registro anulado.
- Componentes de UI compartilhados ficam em `app/ui/`. Os campos de formulário (`Input`, `Select`, `Textarea`, `DateInput`, `MaskedInput`) usam o `Field` (`app/ui/field.tsx`), que liga rótulo, dica (`hint`, ex.: "Opcional") e erro ao controle por `aria-describedby`; campo novo segue o mesmo padrão. O `MaskedInput` usa o `react-imask` com as máscaras de `lib/masks.ts` (`mask="cpf" | "phone" | "cns"`; máscara nova entra no objeto `masks`). Ele é controlado e entrega o valor **sem máscara**, só dígitos, que é o que a API recebe: com o react-hook-form, use-o dentro de um `Controller` (`render={({ field }) => <MaskedInput mask="cpf" {...field} />}`). Para exibir um valor formatado fora de um campo, use `formatWithMask`; em listas, o CPF aparece mascarado com `maskCpf`; em telas de detalhe, CPF e Cartão SUS usam o `SensitiveValue` (`app/ui/sensitive-value.tsx`), mascarado com botão para mostrar. O nome do paciente não vai para o `<title>` da página (fica no histórico do navegador). Datas da API (`AAAA-MM-DD`) são exibidas com `formatDate`/`formatAge` (`lib/dates.ts`), sem passar por `new Date`, para não sofrer com o fuso. Busca digitada vai pelo `useDebouncedValue` e passa pelo `normalizeSearch` (tira a máscara de CPF/CNS); o termo fica no estado do componente, nunca na URL. O `DateInput` usa o seletor nativo, que já devolve `AAAA-MM-DD`. Para listas: `Table` (colunas com `header` e `cell`; no celular cada linha vira um cartão com o nome da coluna ao lado do valor; `isLoading` mostra linhas de `Skeleton`), `Pagination`, `EmptyState` e `Badge` (`tone`). Diálogos: `Modal` usa o `<dialog>` nativo (foco preso, Esc e clique fora fecham, foco devolvido ao fechar; o foco inicial vai para o elemento com `data-autofocus`, já que o `autoFocus` do React não funciona dentro de um `<dialog>` fechado) e `ConfirmDialog` é a confirmação padrão para ações sensíveis (`tone="danger"`; não fecha enquanto `isPending`). O `Checkbox` tem o rótulo ao lado da caixa (aceita links) e liga o erro por `aria-describedby`. O `RadioGroup` é controlado (use-o num `Controller`) e aceita opção desativada; `autoFocusFirst` marca a primeira opção com `data-autofocus`, para abrir um diálogo com o foco nela. Formulário cuja perda custa trabalho (hoje, o novo registro, a edição de registro e o `PatientForm` do cadastro e da edição do paciente, pelo `isDirty`) chama o `useUnsavedChangesWarning(temAlteracoes)` (`hooks/`), que pede confirmação ao seguir link interno, voltar pelo navegador, clicar em "Sair" e recarregar ou fechar a aba; navegação por `router.push` não é interceptada. Formulário em diálogo: envolva o `Modal` num componente com `key` trocada a cada abertura, para ele voltar limpo, e use `form={formId}` no botão de envio do `footer`. O `Button` tem `variant` (`primary`, `secondary`, `danger`) e `block` (padrão: largura total com margem superior, como nos formulários). Telas de erro mostram o código da requisição com `app/ui/request-id.tsx`, para o usuário informar ao suporte.

Alias de importação: `@/*` aponta para a raiz do repositório (ex.: `@/lib/api`, `@/hooks/auth/useLogin`).

## Regras do domínio (LGPD e registro de enfermagem)

O app trata dados sensíveis de saúde. O planejamento, o resumo legal e os acordos com a API (sessão, erros, paginação, rotas) estão em `ROADMAP.md`; em qualquer funcionalidade nova:

- Nunca guardar dados de pacientes em `localStorage`/`sessionStorage`/IndexedDB, URLs (use IDs opacos; nada de nome/CPF em rota ou query string) ou logs/analytics.
- Nada do histórico do paciente é apagado (COFEN): editar um registro cria uma versão nova (as anteriores continuam consultáveis) e "excluir" é **anular** com motivo, de forma definitiva.
- "Excluir paciente" é **arquivar**: o prontuário é mantido pelo prazo legal (Lei 13.787/2018, 20 anos).
- Autoria dos registros (nome + COREN, data/hora) vem da API, nunca de campos editáveis.
- Anexos só por URLs autenticadas/assinadas de curta duração; fotos e vídeos exigem autorização de uso de imagem registrada.
- Coletar apenas os dados necessários (minimização); a autorização real é sempre da API.
